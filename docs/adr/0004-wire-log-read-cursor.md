# 0004 — wire 日志增量读取：进程内 Read Cursor + mtime 预筛

`wire.jsonl` 按增量读取：进程内为每个文件持有 Read Cursor（偏移 / 大小 / mtime / 文件身份 / 未成行尾部字节），每次调用只读自上次以来被追加的字节；另加一层按文件 mtime 的预筛，跳过 mtime 早于保留窗口的文件。**没有任何状态落盘。**

## Status

已采纳（Accepted）。

## Context

- 保留窗口 = `tsMs >= min(当日零点, now − 12h)`，与 mtime 剪枝边界同值。
- 规模（本机实测）：`~/.kimi-code/sessions` 下 25 个 `wire.jsonl`，合计约 45 MiB（实现期记录约 58 MB）；最大单文件约 8.8 MiB。**单行可达数百 KB**——实测最长行约 1.6 MB（源码注释里记录的观察值是 21 KB，是当时样本的上界，不是全局上界）。
- 活跃会话期间文件持续追加（实现期记录约 232 KiB/min）；追加是突发式的，空闲时增长为 0。
- 实测性能：冷启动一次全量约 1.1 s；热路径每次 tick 约 6 ms。
- 全量重扫的代价随历史线性增长：常驻 app 一天里反复扫同一批不断变大的文件，是纯重复劳动，且活跃文件本身就是多 MB 级。
- mtime 预筛之所以成立：记录按时间序追加，所以「mtime 早于保留窗口下界」的文件，其全部记录也必然在窗口之外，可以整文件跳过。
- 为什么必须遍历全部 `agents/*/wire.jsonl`：每个 agent 的文件完全独立、跨文件零重复；只读 `main` 会严重漏计（实测某 session 的 output：main 48k，全部 agent 合计 123k）。

## Considered Options

1. **每次 tick 全量重扫**（否决）：代价随历史无界增长；活跃文件以每分钟数百 KB 增长、单行可达数百 KB，重扫 + 重解析是纯重复劳动。
2. **按 (size, mtime) 缓存解析结果**（否决）：活跃文件一直在长大，缓存键每次都变——结果是反复重读一个多 MB 的文件，等于没缓存。
3. **把游标持久化到磁盘**（否决）：引入新的落盘状态与失效面（进程被杀、日志轮转、时钟变化），而进程重启后一次全量只要约 1.1 s，不值得。
4. **目录 mtime 剪枝 + 跟踪表**（否决）：追加不会更新目录 mtime；若某目录被剪枝而其中文件的游标已退休，「恢复旧会话继续写」会被永久漏计。
5. **增量读取 + 进程内 Read Cursor + 每 tick 全树 walk + 文件 mtime 预筛**（选定）：walk 负责发现新文件与取得 size / inode / mtime，游标负责只读追加字节。

## Decision

- **契约**：`events(now:)` 返回「保留窗口内的 usage 事件集合」，等价于「按当前文件系统状态完整重扫一遍得到的同一集合」。语义是**窗口内全量**，不是「本轮新增」——下游调用方不得假设增量语义。
- Read Cursor 每文件持有 `{offset, size, mtimeMs, identity, carry}`：
  - `offset` 始终停在某个完整行之后；`carry` 持有其后已读入但尚未成行的尾部字节，留到下一次拼接（否则写入中的半行会被永久跳过）。
  - 空行也推进游标，否则偏移会与真实行首位置错位，进而让去重键不稳定。
  - 只读 stat 时点之前的那一段：期间新追加的字节留给下一次调用。
- **失效阶梯**（任一命中即丢弃该文件贡献的窗口内事件并从头重读）：
  - `identity`（APFS inode）变化 → 文件被替换；
  - `size < offset + carry.count` → 被截断；
  - `size == offset + carry.count` 且 mtime 前进 → 原地改写（追加必然改变长度）。
- **游标退休**：walk 没见到的文件（已删除，或 mtime 已滑出剪枝边界）。
- 时钟回拨（保留窗口下界倒退）或 sessions 根缺失 → 清空全部状态，退化一次全量。
- 状态全部在进程内，**不落盘**；不引入 `actor` / `DispatchQueue`，整个 `events(now:)` 由内部 `NSLock` 串行化（60s timer tick 与菜单「立即刷新」可能产生两个重叠 `Task`）。
- 窗口内事件与去重键随 `now` 前进淘汰；头部空洞过大时压缩数组，避免无界增长。
- 测试面：SelfCheck 用临时目录 fixture，断言表达为「增量结果 == 新 reader 的全量结果」+ 明确计数（半行 / 截断 / 替换 / 删除 / mtime 剪枝 / 窗口 / 时钟回拨）。

## Consequences

- 每次刷新与「当天累计日志量」解耦：热路径约 6 ms，冷启动一次约 1.1 s。
- 新增失败面（截断 / 替换 / 半行 / 删除 / 时钟回拨）由 SelfCheck fixture 覆盖；去重键从「全量扫描时从不命中」变为失效重读路径上的护栏。
- mtime 预筛依赖「记录按时间序追加」：若某文件的 mtime 被外部工具回拨到窗口之前而内容仍在窗口内，该文件会被跳过——这是被接受的（不做逐文件内容校验）。
- 进程重启后首次刷新是全量（约 1.1 s），此后转增量；冷启动成本由日志总量决定，会随使用增长。
